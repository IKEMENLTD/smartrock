# 10_技術スタック

基本設計｜技術スタック

要件から推測した主案。承認後に確定

■ 採用スタック（主案）

- レイヤ | 採用技術 | 選定理由
- フロント/画面 | Next.js 14 (App Router) + TypeScript + Tailwind CSS | 顧客LIFF・予約画面・管理画面・APIを1リポジトリで完結。SSR/SEO/LIFF配信に強くClaude Codeでの実装容易性が高い。
- バックエンド | Next.js Route Handlers (Node.js 20) + TypeScript | 画面と同居でAPIを実装。Webhook受信・外部API呼び出しをServer側で完結。
- ジョブ実行 | 専用 worker プロセス + node-cron(1分間隔) + scheduled_tasks テーブル駆動 | createKey/deleteKey/リマインドの時刻起動を、DB永続キューのポーリングで堅牢に実現。Redis不要でMVPに最適。
- DB | PostgreSQL 16 + Prisma ORM | リレーショナルで予約/ログに適合。Prismaでマイグレーションと型安全を確保。
- 認証 | 顧客=LINEログイン(LIFF idToken検証)、管理者=Auth.js(NextAuth) Credentials | 顧客はLINE userIdで識別、管理者はメール+パスワード。
- 外部連携 | LINE Messaging API+LIFF / Google Calendar API(サービスアカウント) / SwitchBot API v1.1 / Stripe(任意) | 要件の連携先。各Service層に隔離(NFR-006)。
- 録画/カメラ | Tapo C320WS・C225 → RTSP → Frigate(別コンテナ) | RTSP/ONVIF対応を活かし自前NVRで月額0。アプリは死活/通知のみ連携。
- インフラ | Docker Compose (app, worker, postgres, frigate) / 店舗オンプレ or VPS | 可搬・再現性。店舗内設置でカメラLANを閉域化しやすい。
■ 代替案

・バックエンド分離案：Next.js(フロント)＋ NestJS/Hono(API/worker)。チーム分業や負荷分離が必要になったら移行。MVPでは同居案を推奨。

・ジョブ：規模拡大時は BullMQ + Redis に置換（scheduled_tasks のインターフェースを保てば差し替え可能）。

⚠ 技術スタックは提案。指定があれば差し替え可。未承認のまま実装に進む場合は本案を既定とする。
